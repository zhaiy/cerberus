# Cerberus Iteration 5 方向规划与开发计划

_最后更新：2026-04-08_

## 1. 规划结论

第五期不建议再做“新功能扩张型”迭代，而应进入：

**“Agent 运维可见性与调用规范”阶段。**

换句话说，重点不再是“再多做几个命令”，而是把 Cerberus 从“可供 agent 使用”继续推进到“agent 更不容易误用、出错后更容易判断、复盘时更容易理解”。

## 2. 为什么是这个方向

第四期完成后，Cerberus 已经具备：

- 稳定的维护命令 JSON 输出
- 基础可区分的退出语义
- 最小必要的高风险操作日志
- 可通过的维护链路验收

此时最有价值的增量，不是 UI，也不是额外业务功能，而是 3 件事：

1. 让 agent 在失败时得到更稳定的结构化错误结果。
2. 让人和 agent 都能查询“最近发生了什么”。
3. 让调用顺序和推荐姿势文档化，而不是依赖读代码或猜测。

## 3. 第五期主题

第五期主题建议定为：

**“可观测维护接口与 Agent 调用规范”**

核心目标：

- 高风险命令具备统一错误包络
- 审计日志可以通过命令查询
- agent 有明确的推荐调用顺序
- 真实恢复演练从“测试通过”升级为“有复盘记录”

## 4. 第五期范围

### In Scope

- 统一的 JSON 错误包络
- `ops list` / `ops show` 操作日志查询命令
- Agent 推荐调用顺序文档
- 恢复演练复盘模板与一次真实演练文档
- 对现有维护命令补充失败路径和一致性测试

### Out of Scope

- Web UI
- TUI
- 云同步
- 语义搜索
- 多用户协作
- 远程审计上报

## 5. 阶段规划

### Phase 1：统一错误包络

目标：

- 让维护命令在 `--json` 模式下失败也返回稳定结构

建议交付物：

- 通用 JSON error envelope
- `code` / `message` / `retryable` / `details` 等稳定字段
- README 中的失败样例

验收标准：

- 关键维护命令失败时，脚本不必依赖 stderr 自由文本
- 退出码和 JSON 错误字段表达同一结论

### Phase 2：操作日志查询命令

目标：

- 把底层 `operations.log` 提升为正式 CLI 能力

建议交付物：

- `cerberus ops list`
- `cerberus ops show <id>`
- `--json` 输出
- 基础筛选：最近 N 条、命令类型、成功/失败

验收标准：

- 不直接要求用户手读日志文件
- 能快速定位最近一次 restore/import/cleanup 的结果

### Phase 3：Agent 调用规范文档

目标：

- 显式告诉 agent “应该先做什么，再做什么”

建议交付物：

- 推荐调用顺序文档
- 常见维护场景 SOP
- 错误恢复建议

建议覆盖场景：

- 新 vault 初始化
- 日常使用
- 备份校验
- 恢复前检查
- 导出导入回环
- cleanup 前后检查

验收标准：

- 一个不读源码的 agent 也能按文档完成主流程
- 文档能减少误用和顺序错误

### Phase 4：真实恢复演练与复盘

目标：

- 把“自动化测试通过”提升到“真实场景可复盘”

建议交付物：

- 恢复演练记录文档
- 演练前条件、步骤、结果、异常、回滚点
- 是否建议纳入发布门槛的明确结论

验收标准：

- 至少完成 1 次真实目录级恢复演练
- 复盘文档足以让他人重复

## 6. 建议任务拆卡

### Task 1：统一 JSON 错误包络

适合模型：

- `gpt-5.4`
- `gpt-5.3-codex`

原因：

- 需要同时考虑 CLI 契约、错误语义、一致性和测试补强

### Task 2：操作日志查询命令

适合模型：

- `gpt-5.3-codex`
- `gpt-5.4-mini`

原因：

- 逻辑中等复杂，要求边界稳定，适合偏稳的实现型模型

### Task 3：Agent 调用规范文档

适合模型：

- `gpt-5.4`
- `gpt-5.2`

原因：

- 更偏文档结构、运维视角和用户路径梳理

### Task 4：恢复演练与复盘

适合模型：

- `gpt-5.4`

原因：

- 涉及真实链路、异常假设、执行与文档闭环，适合更稳的模型

## 7. 第五期优先级建议

### Priority 1

- 统一 JSON 错误包络
- 操作日志查询命令

原因：

- 这两项会直接提升 agent 集成稳定性
- 也是当前“最接近缺一块”的工程收口项

### Priority 2

- Agent 调用规范文档
- 真实恢复演练复盘

原因：

- 这两项更偏“提升可托付感”
- 价值很高，但不一定先于错误包络和日志查询

## 8. 测试要求

第五期建议至少满足：

- 统一错误包络的单元测试
- `ops list/show` 的命令级测试
- 失败路径下 JSON 输出稳定性测试
- 文档示例可执行性验证

重点测试：

- `--json` 成功与失败输出都稳定
- `ops` 查询不泄漏敏感内容
- `ops show` 能准确定位对应命令执行结果
- 推荐调用顺序文档中的示例命令能够真实执行

## 9. 完成定义

当以下条件都满足时，可认为第五期完成：

- 关键维护命令失败时也有统一 JSON 包络
- 操作日志可通过正式命令查询
- agents 有清晰、可执行的调用顺序文档
- 至少 1 次真实恢复演练完成并留有复盘

## 10. 第五期后的中期方向

如果第五期顺利完成，我建议中期方向按以下顺序考虑：

1. 审计日志筛选和时间范围过滤增强
2. timeline / today 等可读性命令
3. 语义搜索
4. 更远期的 TUI，而不是先做 Web UI
