# Cerberus Iteration 4 开发计划

_最后更新：2026-04-08_

## 目标

第四期聚焦"CLI 契约稳定与运维可信度"，把当前产品从"功能已闭环"推进到"更适合 agents 长期调用和复盘"。

核心目标：

- 关键维护命令具备稳定的机器可读输出
- 高风险命令具备更清晰的错误与退出语义
- restore / import / cleanup 等操作可被本地追溯
- 端到端演练与发布验收更可信

## 实施状态

**完成	date: 2026-04-08**

- Phase 1: 维护命令 JSON 契约补齐 ✓
- Phase 2: 错误与退出码整理 ✓
- Phase 3: 高风险操作日志 ✓
- Phase 4: 集成演练与发布验收 ✓

## 范围

### In Scope

- `backup verify --json`
- `backup restore --dry-run --json`
- `import --json`
- `doctor cleanup --json`
- 关键错误码与帮助信息整理
- 高风险操作日志
- 关键维护链路的集成验收补强

### Out of Scope

- Web UI
- TUI
- 云同步
- 语义搜索
- 多用户协作
- 远程日志上报

## 拆分原则

- 先稳契约，再补运维追溯
- 每个阶段都应可独立验收
- 对日志与错误输出同样保持保守默认
- 不为 UI 预埋复杂交互抽象

## 阶段规划

### Phase 1：维护命令 JSON 契约

目标：

- 补齐维护命令的机器可读输出

交付物：

- `backup verify --json`
- `backup restore --dry-run --json`
- `import --json`
- `doctor cleanup --json`
- 文本输出与 JSON 输出的一致性约束

验收标准：

- 关键命令无需依赖脆弱文本解析
- JSON 字段稳定、可预测、可测试

### Phase 2：错误与退出码整理

目标：

- 让失败结果更适合 shell 和 agent 判断

交付物：

- 高风险命令错误分类梳理
- README / help / 测试同步
- 常见错误路径的退出语义验证

验收标准：

- 参数错误、状态错误、校验失败可以区分
- 高风险命令失败时不需要人工阅读长文本才能判断类型

### Phase 3：本地操作日志

目标：

- 为高风险操作提供最小必要审计

交付物：

- backup / restore / import / cleanup 的操作摘要记录
- 安全边界说明
- 基础查询或可读文件格式定义

验收标准：

- 日志不包含正文或密码
- 日志足以复盘“何时、对哪个目录、执行了什么、结果如何”

### Phase 4：集成演练与发布验收

目标：

- 提升“恢复闭环已真正验证”的可信度

交付物：

- 恢复主链路集成测试
- 导入回环测试
- cleanup 保守边界回归测试
- README 中的发布验收建议

验收标准：

- 至少一条恢复链路能端到端通过
- 至少一条导出导入回环可稳定复现
- cleanup 不会误删非孤儿数据

## 建议顺序

1. maintenance `--json`
2. 错误与退出码整理
3. 操作日志
4. 集成演练与验收

## 建议模型分配

为了降低并行开发时的耦合，建议按任务性质分配：

1. maintenance `--json`
   建议：`gpt-5.4` 或 `gpt-5.3-codex`
   原因：需要同时处理 CLI 输出、人类可读文本和机器契约的一致性。
2. 错误与退出码整理
   建议：`gpt-5.3-codex`
   原因：更偏系统梳理、边界归类和测试补强。
3. 操作日志
   建议：`gpt-5.4-mini` 或 `gpt-5.3-codex`
   原因：逻辑不一定复杂，但对日志内容边界很敏感。
4. 集成演练与验收
   建议：`gpt-5.4`
   原因：涉及真实链路、环境假设和文档闭环，适合更稳的模型。

## 测试要求

本期每一阶段都建议至少满足：

- 单元测试覆盖字段和边界条件
- 集成测试覆盖主链路
- 对错误路径有最小必要验证

重点测试：

- `--json` 输出结构稳定
- 参数错误与状态错误的退出语义
- 操作日志不泄漏敏感内容
- restore / import / cleanup 的端到端演练

建议额外覆盖：

- 文本输出与 JSON 输出表达同一结论
- 高风险命令失败后也会产生日志摘要或明确不产生日志
- README 中示例命令可被真实执行验证

## 完成定义

当以下条件都满足时，可认为四期完成：

- 关键维护命令具备稳定 JSON 输出
- 高风险失败场景具备清晰退出语义
- 本地操作日志可用于最小复盘
- 关键维护链路有可信的集成演练

## 1.0 候选发布门槛

如果第四期按计划完成，我会更愿意把 Cerberus 视为第一个可供 agents 长期使用的 `1.0` 候选。

### 功能门槛

- 备份、校验、恢复链路可重复演练
- 导出、导入链路可重复演练
- doctor 与 cleanup 结论既可读也可机读
- 高风险操作具备最小必要审计

### 质量门槛

- `npm run check` 与 `npm test` 稳定全绿
- 维护命令 JSON 契约有测试兜底
- 高风险命令默认保守，不覆盖、不删除、不隐式修复
- 错误与退出码可以稳定被脚本消费

### 发布门槛

- `README.md` 覆盖全部关键维护命令的文本/JSON 用法
- 明确写出“不做 UI，以 CLI/agents 为主”的产品边界
- 至少完成一次真实恢复演练复盘

## 1.0 前仍建议补的点

1. 操作日志是否需要查询命令，而不仅是底层文件。
2. 是否要为所有高风险命令提供统一 JSON 错误包络。
3. 是否要补一条跨目录、跨机器的真实恢复说明。
4. 是否要为 agents 提供更明确的“推荐调用顺序”文档。
