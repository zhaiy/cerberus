# Cerberus Iteration 3 开发评审

_评审日期：2026-04-05_
_评审对象：第三期开发结果（原始提交状态，后续已进行修复）_

## 1. 评审范围

本次评审覆盖第三期规划中的以下能力：

- `backup restore`
- `import --format json|markdown`
- `doctor check`
- `doctor cleanup`

评审口径沿用本项目此前约定的 6 个维度：

1. 需求符合度
2. 安全边界
3. 测试可信度
4. 代码边界
5. 脚本友好度
6. 文档完成度

## 2. 评分结果

| 维度 | 分数 | 评价 |
|---|---:|---|
| 需求符合度 | 6/10 | 主功能基本落地，但 `doctor cleanup` 明显偏离“仅清理明确孤儿项”的任务边界。 |
| 安全边界 | 3/10 | 存在 2 个 P1 级问题，都会把“维护命令”推向误删风险。 |
| 测试可信度 | 5/10 | 覆盖了主链路和部分错误路径，但没有拦住最关键的安全语义回归。 |
| 代码边界 | 7/10 | 模块拆分总体清晰，改动面基本聚焦在对应命令和服务层。 |
| 脚本友好度 | 6/10 | 新命令输出可读，`doctor check --json` 也已补齐，但契约稳定性仍不足。 |
| 文档完成度 | 6/10 | README 和任务文档有同步，但文档承诺与实际行为一度不一致。 |

## 3. 总结判断

综合评价：**5.5/10，属于“功能基本完成，但不建议按原样合并”的一轮开发。**

这轮开发的优点是推进速度快，功能覆盖面达到了第三期的大部分目标，尤其是 `backup restore` 的实现结构相对完整，测试也补得比较主动。

主要问题集中在 `doctor`：

- 对“保守默认”的理解不够严格
- 对既有 soft delete 语义缺少敬畏
- 测试更偏向“功能能跑通”，对高风险边界缺乏逆向验证

这意味着它更像一轮“把功能做出来”的开发，而不是一轮“把维护能力做稳”的开发。

## 4. 关键发现

### 4.1 P1：soft delete 保留的密文被误判为孤儿文件

问题表现：

- `doctor check` 只把 `deleted_at IS NULL` 的 entry 当作有效引用
- 已软删除但仍保留在磁盘上的密文会被标记为 `orphan_entry_file`
- `doctor cleanup --apply` 会进一步删除这些文件

影响：

- 破坏了既有“软删除只删元数据可见性、不删密文”的产品约定
- 维护命令可能导致不可逆的数据丢失

### 4.2 P1：cleanup 删除了超出文档承诺范围的元数据

问题表现：

- 文档与任务卡要求 cleanup 只处理“明确孤儿项”
- 实现里却会删除“缺失密文对应的 entry / attachment 记录”

影响：

- 一旦文件只是暂时缺失、移动错误或可从备份恢复，metadata 会被永久抹掉
- 这不是“保守清理”，而是高风险破坏性修复

### 4.3 P2：`doctor check` 并非真正只读

问题表现：

- `doctor check` 调用了 migration
- 这会修改 `db.sqlite`、推进 schema 状态，并可能掩盖原始问题

影响：

- 诊断命令的可信度下降
- “检查”与“修复”语义被混在一起

## 5. 与既有代码质量对比

结论：**这次开发质量略差于项目中此前已经存在的实现。**

原因不是代码风格更差，而是它在最关键的地方踩错了边界：

- 既有代码整体更尊重“默认保守”的产品约束
- 这轮开发在 `doctor` 上把“辅助维护”做成了“可能扩大损失”的命令
- 从项目成熟度视角看，这类问题比普通逻辑 bug 更严重

如果只看“功能推进速度”，这轮表现不差；如果看“是否值得托付高风险命令”，则不如既有实现稳妥。

## 6. 复盘结论

第三期开发暴露出一个很明确的经验：

> 对 Cerberus 这类本地加密、维护命令敏感的 CLI，评审重点不能只看“功能有没有做出来”，而必须优先看“错误时会不会误删、误修、误覆盖”。

后续给 LLM 下发任务时，建议继续沿用这 6 个维度，并额外强调两条：

1. 对高风险命令，默认行为必须比文档更保守，而不是更激进。
2. 测试需要专门覆盖“误删、误修、误覆盖”的反向样例。

## 7. 后续处理结果

本次评审识别出的 3 个问题已在评审后补做修复，包括：

- `doctor check` 改为真正只读
- soft delete 保留密文不再误报为 orphan
- `doctor cleanup --apply` 仅删除明确孤儿密文文件

因此，本文件保留的是**开发原始质量评估**，而不是修复后的最终仓库质量评分。
