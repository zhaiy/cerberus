# Cerberus Iteration 5 任务卡

_最后更新：2026-04-08_

## 用途

本文件用于将 Cerberus 第五期迭代拆成更适合分发给不同 LLM 的任务卡。

本期主题：

- 统一 JSON 错误包络
- 操作日志查询命令
- Agent 调用规范文档
- 真实恢复演练与复盘

## 使用方式

每次下发任务建议附带：

1. 当前技术方案：`PROJECT.md`
2. 第五期计划：`ITERATION_5_PLAN.md`
3. 第四期最终验收：`ITERATION_4_FINAL_ACCEPTANCE.md`
4. 本文档中对应任务卡
5. 仓库当前代码状态

## 推荐分发策略

第五期仍然适合拆卡，而不是整期一次性交给单个模型：

1. 用更稳的模型做统一 JSON 错误包络
   建议：`gpt-5.4`。
2. 用更擅长工程收口的模型做操作日志查询命令
   建议：`gpt-5.3-codex`。
3. 用偏稳妥的模型做 Agent 调用规范文档
   建议：`gpt-5.4` 或 `gpt-5.2`。
4. 用更强的模型做真实恢复演练与复盘
   建议：`gpt-5.4`。

本期重点不在 UI，而在“是否更适合 agents 长期托付”。比较模型时，建议优先看：

- 错误契约的一致性
- 运维查询能力的边界控制
- 文档是否真能指导 agent
- 测试与复盘是否可信

## 任务卡列表

### Task Card 1：统一 JSON 错误包络

适合模型：

- `gpt-5.4`
- `gpt-5.3-codex`

```md
# Task Card 1：统一 JSON 错误包络

## 目标

请为关键维护命令补统一的 JSON 错误包络。

## 本次范围

- `backup verify --json`
- `backup restore --json`
- `import --json`
- `doctor cleanup --json`
- JSON 模式下的失败输出

## 不在范围内

- 不重构整个 CLI 框架
- 不把所有命令都扩展为 `--json`
- 不修改底层业务语义

## 可修改文件范围

- `src/commands/**`
- `src/services/**`
- `src/core/errors.ts`
- `tests/**`
- `README.md`

## 实现要求

- 成功与失败都要有稳定结构
- JSON 错误字段命名统一
- 退出码与 JSON 错误结论一致
- 不泄漏敏感信息或本地绝对路径

## 输出要求

- 完成代码修改
- 补最少必要测试
- 简述包络设计
- 列出兼容性风险和未覆盖项

## 验收标准

- 关键维护命令失败时也能被脚本稳定消费
- 错误 JSON 结构有测试覆盖
- README 有成功与失败示例
```

### Task Card 2：操作日志查询命令

适合模型：

- `gpt-5.3-codex`
- `gpt-5.4-mini`

```md
# Task Card 2：操作日志查询命令

## 目标

请把现有 `operations.log` 提升为正式 CLI 能力。

## 本次范围

- `cerberus ops list`
- `cerberus ops show <id>`
- `--json` 输出
- 基础筛选：最近 N 条、按命令类型、按成功/失败

## 不在范围内

- 不做远程日志
- 不做复杂图形界面
- 不改动现有高风险命令的业务语义

## 可修改文件范围

- `src/cli/**`
- `src/commands/**`
- `src/core/operation-log.ts`
- `src/services/**`
- `tests/**`
- `README.md`

## 实现要求

- 查询能力默认只读
- 输出中不泄漏正文、附件明文、密码
- 文本与 JSON 输出都要可读
- 对日志不存在、ID 不存在等情况给出明确错误语义

## 输出要求

- 完成代码修改
- 补最少必要测试
- 简述命令设计与字段设计
- 列出风险、假设和未完成项

## 验收标准

- 不需要用户手读底层日志文件
- 能查询最近一次 restore/import/cleanup 的摘要
- `ops` 命令主路径与错误路径有测试覆盖
```

### Task Card 3：Agent 调用规范文档

适合模型：

- `gpt-5.4`
- `gpt-5.2`

```md
# Task Card 3：Agent 调用规范文档

## 目标

请编写一份面向 agents 的推荐调用顺序与维护 SOP 文档。

## 本次范围

- 新 vault 初始化
- 日常使用基本顺序
- 备份与校验
- 恢复前检查与恢复后验证
- 导出导入回环
- doctor / cleanup 的推荐使用顺序

## 不在范围内

- 不改动底层代码逻辑
- 不写超出当前实现能力的宣传性文档
- 不扩展到 UI 场景

## 可修改文件范围

- `docs/**`
- `README.md`

## 实现要求

- 文档面向 agent 和自动化调用，不是普通营销文案
- 明确“推荐顺序”“危险动作前置检查”“失败后如何判断”
- 真实反映当前支持范围
- 避免要求 agent 猜测命令行为

## 输出要求

- 完成文档修改
- 简述文档结构
- 列出仍然依赖人工判断的环节

## 验收标准

- 一个不读源码的 agent 也能按文档完成主流程
- 文档能显著降低误用和顺序错误
- README / docs 不互相矛盾
```

### Task Card 4：真实恢复演练与复盘

适合模型：

- `gpt-5.4`

```md
# Task Card 4：真实恢复演练与复盘

## 目标

请完成一次真实恢复演练，并留下可复盘文档。

## 本次范围

- 备份 -> 校验 -> 恢复 -> 解锁 -> list
- 演练前条件记录
- 演练步骤记录
- 结果与异常记录
- 发布门槛建议

## 不在范围内

- 不做云端环境依赖
- 不引入 UI 演示
- 不把演练文档写成脱离当前实现的宣传材料

## 可修改文件范围

- `docs/**`
- `README.md`
- `tests/**`

## 实现要求

- 复盘应真实反映执行结果
- 明确写出哪些环节已验证，哪些还没有
- 若补测试，只补与演练链路直接相关的最小必要测试

## 输出要求

- 完成演练与文档记录
- 简述执行环境与结论
- 列出风险、例外和未完成项

## 验收标准

- 至少完成 1 次真实目录级恢复演练
- 文档足以让他人重复该演练
- 对是否应纳入发布门槛有明确建议
```
