# Cerberus Roadmap

_最后更新：2026-04-08_

## 1. 当前状态

第四期验收完成后，Cerberus 已具备：

- 条目与附件的本地加密存储
- 会话控制与脚本化基础
- 备份、校验、恢复闭环
- 导出、导入闭环
- `doctor check` 与保守 `cleanup`
- 关键维护命令稳定 JSON 输出
- 高风险操作最小必要审计
- 维护命令验收测试与 README 同步
- 基础 JSON 输出与 Skill 接入

当前更值得投入的方向，不是 UI，而是把这套 CLI 从“稳定接口”继续推进到“更可观测、更不易误用的维护接口”。

## 2. 当前迭代重点

### Priority 1

#### 2.1 统一 JSON 错误包络

- 关键维护命令失败时也输出稳定 JSON
- 错误字段命名统一
- 退出码与 JSON 语义一致

理由：

- agents 不仅怕“成功输出不稳定”，也怕“失败输出不可预测”
- 当前已经完成成功态 JSON，下一步最值得补失败态契约

#### 2.2 操作日志查询命令

- `cerberus ops list`
- `cerberus ops show`
- `--json` 输出

理由：

- 审计日志现在只有底层文件，仍不够像正式 CLI 能力
- 查询命令会显著提高复盘效率和自动化可用性

### Priority 2

#### 2.3 Agent 调用规范文档

- 推荐调用顺序
- 常见维护场景 SOP
- 错误恢复建议

理由：

- 当前仓库已适合 agent 调用，但“如何正确调用”仍分散在代码和 README 中
- 明确规范会减少误用与重复试探

#### 2.4 真实恢复演练复盘

- 跨目录恢复演练
- 演练复盘模板
- 发布门槛建议

理由：

- 自动化测试已全绿，但真实演练记录仍偏少
- 没有复盘记录，长期托付感仍然不足

## 3. 1.0 发布候选判断

在第四期完成后，Cerberus 已达到 `1.0` 候选质量，我更倾向把第五期视为“1.0 前的可运维性增强”。

建议至少满足：

- 关键维护命令有稳定 JSON 输出
- 高风险失败场景有明确退出码
- 至少一条恢复主链路有可重复的集成验收
- cleanup 的保守边界有回归测试兜底
- README 与 help 不再落后于实现

如果第五期也顺利完成，我会更愿意把 Cerberus 视为“对 agents 更可托付的 `1.0` 候选”，而不只是“功能可靠的 CLI”。

## 4. 1.0 前仍建议补的非功能点

### 4.1 CLI 契约

- 明确列出成功与失败都支持 JSON 的命令范围
- 保证 JSON 输出字段稳定
- 给失败结果统一错误包络

### 4.2 运维可信度

- 高风险命令形成正式可查询的审计链
- 真实恢复演练至少做一次
- 文档里明确哪些能力“已验证”，哪些只是“已实现”

### 4.3 安全边界

- 不隐式覆盖
- 不隐式删除
- 不隐式修复
- 不把敏感内容写入日志

## 5. 中期候选项

### 5.1 时间线视图

- `cerberus timeline`
- `cerberus today`

这仍然更适合在 CLI 内继续推进，而不是做 GUI。

### 5.2 语义搜索

方向：

- 本地 embedding
- 受控索引
- 不暴露原文

价值仍然存在，但优先级低于契约稳定与运维可信度。

## 6. 长期探索

- 本地审计快照
- Shamir 密钥分片恢复
- 时间锁
- 双向链接
- 只读分享包
- TUI

## 7. 风险提醒

- 当前阶段不做 UI，不代表未来完全不做，而是优先级明确靠后
- 任何给 agents 使用的命令，都应优先输出稳定契约
- 任何运维日志设计，都不能引入新的敏感信息泄漏面
