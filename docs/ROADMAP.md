# Cerberus Roadmap

_最后更新：2026-04-05_

## 1. 当前状态

前三期之后，Cerberus 已具备：

- 条目与附件的本地加密存储
- 会话控制与脚本化基础
- 备份、校验、恢复闭环
- 导出、导入闭环
- `doctor check` 与保守 `cleanup`
- 基础 JSON 输出与 Skill 接入

当前更值得投入的方向，不是 UI，而是把这套 CLI 打磨成适合 agents 长期调用的“稳定接口”。

## 2. 当前迭代重点

### Priority 1

#### 2.1 维护命令 JSON 契约补齐

- `backup verify --json`
- `backup restore --dry-run --json`
- `import --json`
- `doctor cleanup --json`

理由：

- agents 最怕“输出看起来可读，但结构不稳定”
- 这些命令都属于自动化中最容易被串起来的维护链路

#### 2.2 错误语义与退出码收敛

- 高风险命令失败分类
- README / help / 测试同步

理由：

- 没有稳定退出语义，agent 只能靠脆弱文本判断失败类型
- 这会直接影响自动恢复和巡检流程

### Priority 2

#### 2.3 高风险操作日志

- `backup create`
- `backup restore`
- `import`
- `doctor cleanup`

理由：

- 这些命令都值得被复盘
- 审计不应等到将来做 UI 才考虑

#### 2.4 端到端验收与演练

- 恢复演练
- 导入回环
- cleanup 边界回归

理由：

- 当前已经接近可托付，但“真实演练”仍偏少
- 没有演练，1.0 的可信度仍然不足

## 3. 1.0 发布候选判断

在第三期功能完成后，Cerberus 已接近 `1.0` 候选，但我更倾向把第四期视为“1.0 前的可靠性收口”。

建议至少满足：

- 关键维护命令有稳定 JSON 输出
- 高风险失败场景有明确退出码
- 至少一条恢复主链路有可重复的集成验收
- cleanup 的保守边界有回归测试兜底
- README 与 help 不再落后于实现

如果这些点还没有齐，我会更倾向于 `0.9.x` 而不是 `1.0`。

## 4. 1.0 前仍建议补的非功能点

### 4.1 CLI 契约

- 明确列出支持 `--json` 的命令范围
- 保证 JSON 输出字段稳定
- 错误输出不要混入多余人类描述

### 4.2 运维可信度

- 高风险命令形成最小审计链
- 真实恢复演练至少做一次
- 文档里明确哪些能力“已验证”，哪些只是“已实现”

### 4.3 安全边界

- 不隐式覆盖
- 不隐式删除
- 不隐式修复
- 不把敏感内容写入日志

## 5. 中期候选项

### 5.1 审计日志查询

- `cerberus ops list`
- `cerberus ops show`

前提是本地操作日志能力先稳定。

### 5.2 时间线视图

- `cerberus timeline`
- `cerberus today`

这仍然更适合在 CLI 内继续推进，而不是做 GUI。

### 5.3 语义搜索

方向：

- 本地 embedding
- 受控索引
- 不暴露原文

价值仍然存在，但优先级低于契约稳定与运维可信度。

## 6. 长期探索

- 本地审计快照
- Shamir 密钥分片恢复
- 时间锁
- 双向链接
- 只读分享包
- TUI

## 7. 风险提醒

- 当前阶段不做 UI，不代表未来完全不做，而是优先级明确靠后
- 任何给 agents 使用的命令，都应优先输出稳定契约
- 任何运维日志设计，都不能引入新的敏感信息泄漏面
